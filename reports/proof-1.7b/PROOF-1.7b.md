## 2. Reference oracle and the encoder attention window

The oracle is the unmodified official `Qwen3ASRProcessor` and `Qwen3ASRForConditionalGeneration` from the pinned QwenLM/Qwen3-ASR revision, FP32, eager attention, greedy decoding, on CPU. One documented adjustment is applied through the layer call, not by editing the official source:

- The official `Qwen3ASRAudioEncoder` defines `_prepare_attention_mask` (block-diagonal windows of `n_window_infer = 800` mel frames = 104 encoder tokens) and passes `cu_seqlens` to every layer, but the eager/SDPA path never applies the mask, so the encoder attends globally across the whole utterance. The flash-attention path of the same file and the transformers-integrated implementation (`get_audio_cu_seqlens`, per-window attention on the non-flash path) both attend within windows, and the pinned ONNX export implements the windowed behaviour.
- `scripts/reference.py` therefore applies the official `_prepare_attention_mask` output when a layer is called without a mask. `--global-attention` reproduces the unmasked pinned path; its outputs are kept in `reports/reference-global-attention/` for comparison.

Measured on `mandarin-0000` (1038 mel frames, 135 encoder tokens):

|---|---|---|---|
| official direct vs official generate trace | 0.00e+00 | 0.00e+00 | 0.0211 |
| official vs wrapper | 1.80e-01 | 1.06e-02 | 0.0211 |
| wrapper vs onnx native | 8.57e-07 | 6.28e-08 | 0.0215 |

## 3. Stage-by-stage verification

- Tokenizer: 8/8 frozen prompt/text/EOS cases match the official tokenizer (`reports/tokenizer.json`). The executable re-checks these cases at every model load.
- Preprocessing: 29/29 boundary, PCM-format and resampling cases pass (`reports/preprocessing.json`).
- Fixture frontend: 24/24 fixtures match the official mel features and audio-token counts (`reports/fixture-frontend.json`).
- Speech gate: 6/6 non-speech cases produce no segments (`reports/speech-gate.json`).
- Invalid input: 12/12 malformed-input and missing-asset cases exit nonzero with explicit errors (`reports/cli-failures.json`).

Tolerances (`verification-policy.json`):

| Stage | absolute | relative (per element) | scale-relative (× max|ref|) | RMSE-relative (× RMS ref) |
|---|---|---|---|---|
| pcm | 1e-07 | 0.0 | - | - |
| mel | 0.0001 | 0.0001 | - | - |
| encoder | 0.002 | 0.0001 | - | - |
| input_embeds | 0.002 | 0.0001 | - | - |
| logits | 0.005 | 0.0001 | - | - |
| keys | 0.003 | 0.0001 | 0.001 | 0.001 |
| values | 0.003 | 0.0001 | 0.001 | 0.001 |

A stage passes when every element satisfies |native-reference| <= absolute + relative*|reference|. Stages that also define scale_relative/rmse_relative pass alternatively when max|native-reference| <= absolute + scale_relative*max|reference| and RMSE <= rmse_relative*RMS(reference) over the whole tensor. Shapes must match exactly and all elements must be finite.

Tolerance change (2026-09-07, keys, values): added tensor-scale criterion (scale_relative 1e-3, rmse_relative 1e-3). Reason: Decoder KV caches contain attention-sink outliers with magnitudes up to about 390 (keys) and 143 (values). FP32 accumulation-order differences between ONNX Runtime fused kernels and PyTorch eager appear as absolute noise of up to 0.06 spread over the tensor, not proportional to the individual element, so the element-wise rule fails on elements near zero although the tensor agrees to about 1e-4 of its scale. The decision quantity (logits) still meets the original element-wise tolerance (max error about 2e-4 against 0.005) and all 24 token sequences are identical to the oracle. Encoder, input_embeds, logits, mel and pcm tolerances are unchanged.

The p95 provisional-lag target is **not met** in 2 of 5 runs (live-mandarin-0003, capture-3min-load2): with the FP32 1.7B decoder at about 140 ms per token, a provisional decode of a 10–15 s Mandarin snapshot takes 3–5 s, and finalization of a 15 s utterance 5–9 s. The int4 decoder is about 3× faster but was rejected by the held-out accuracy rule (section 4); this limitation is published as measured. Memory is reported in both binary and decimal units because the target does not state which; the peak is below 16 GiB and slightly above 16 GB.

Remaining gaps:

- Clean-Windows verification on external machines has not been performed; the package is a test candidate and no clean-install or real-time support claim is made.
- DirectML is disabled: it has not passed regression and sustained-load tests on any adapter/driver combination.
- Sustained live measurements exist only for the reference PC; see `docs/COMPATIBILITY.md`.
